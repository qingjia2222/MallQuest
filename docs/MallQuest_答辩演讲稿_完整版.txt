MallQuest 商场 AI 私域服务助手——答辩演讲稿（完整版）

适用方式
========

本稿按建议扩充后的 15 页主讲结构编写，完整讲述约 15～18 分钟。若现场只给 8～10 分钟，可优先讲第 1、3、5、6、7、9、11、12、13 页，其余内容作为老师追问时的补充。

答辩中的统一口径：

1. 项目是课程 Demo，但核心链路是真实实现，不是静态页面演示。
2. 在线大模型使用通义千问 qwen-plus，通过 OpenAI-compatible API 接入；网络或模型不可用时自动降级到 scripted agent。
3. 店铺、排队、预约、优惠券、方案等业务事实来自 SQLite 私有数据源，不由大模型编造。
4. 积分规则、商场服务指南等稳定的非结构化内容使用本地 RAG 知识库。
5. 地图底图和坐标是星河里课程 Demo 仿真数据，但走廊图、障碍约束、Dijkstra 路径和跨层换乘是真实计算。
6. 预约、领券、票券等事务在课程中真实写入演示数据库，但没有连接真实支付、影院、停车硬件或商业 POS 系统。
7. 管理驾驶舱的日/月/年经营指标是稳定、可复现的演示快照，不宣称来自真实客流设备。


第 1 页：封面
============

各位老师好，我们是 MallQuest 项目组。今天汇报的项目是“商场 AI 私域服务助手”。

我们想解决的不是单独做一个聊天机器人，而是把商场里原本分散的店铺信息、停车、会员积分、优惠券、预约、路线和经营管理能力，统一接入一个可以理解自然语言、能够调用真实业务工具、并且能在用户确认后完成事务的大模型服务入口。

项目同时提供微信原生小程序和 Vue Web 两个客户端。两端共用同一套 FastAPI 后端、同一套身份与会话体系、同一份私有数据库和同一份地图路网，所以它们不是两套彼此独立的演示页面。


第 2 页：汇报提纲
================

本次汇报分为四个部分。

第一部分介绍项目背景和我们要解决的真实问题；第二部分展示系统功能和完整业务闭环；第三部分说明总体架构、LLM 编排、私有数据、RAG、地图路线、事务安全和技术选型；第四部分汇报测试结果、当前边界和后续扩展方向。

我们会重点回答三个问题：第一，大模型在系统里到底做了什么，而不是只生成一段文字；第二，大模型如何安全访问商场私有数据并完成真实业务动作；第三，系统如何保证小程序、Web、方案卡片、地图路线和最终事务结果保持一致。


第 3 页：项目背景——为什么需要这个系统
====================================

传统商场服务主要存在四类问题。

第一，信息分散。店铺、停车、优惠、会员和活动信息常常分布在导览牌、公众号、各商户系统和人工服务台中，顾客必须在多个入口之间寻找。

第二，更新滞后。纸质导览和静态页面不能及时反映营业状态、排队时间、剩余座位和优惠库存。

第三，跨商户协调困难。顾客真正提出的需求通常不是“查一家店”，而是“今晚两个人约会，人均二百，希望先吃饭再喝咖啡，而且少走路”。这需要同时组合多家店铺、时间、预算、排队和路线，传统关键词搜索很难完成。

第四，服务方式被动。传统系统通常只能回答单个问题，不能持续记住用户的人数、时间、预算和偏好，更不能在确认后继续完成预约、领券等动作。

因此我们的定位是：顾客在商场内扫码或网页登录，只需要用自然语言表达目标；大模型负责理解和编排，后端负责真实数据、权限、路线和事务，最终形成“理解、采集、规划、绘制路线、确认、执行”的闭环。


建议新增第 4 页：三类用户与商业价值
==================================

系统服务三类角色，并且三类角色使用相互独立的入口和权限。

第一类是游客或会员。他们可以查店、查停车、问积分规则、看优惠、预约餐厅、规划行程并查看地图导航。

第二类是商户。商户通过商场分配的店铺编码换取商户会话，只能维护自己被授权的店铺，包括营业状态、排队分钟、剩余座位、优惠套餐和代金券活动。商户修改后，游客端地图和 LLM 查询会读取同一份数据，因此可以立即看到变化。

第三类是商场管理者。管理者通过管理账号进入驾驶舱，可以查看经营分析、创建店铺及店铺编码，并人工维护系统提示词。管理者无法越权成为商户，商户也不能访问管理接口。

对商场而言，价值不是简单增加一个聊天窗口，而是形成统一私域数据底座：前端面向顾客提供智能导购和路线转化，商户自行维护实时状态，管理端形成经营观察入口。未来接入新商场时，主要替换 mall_id 对应的数据适配器和地图资源，不需要重写整套问答与事务流程。


第 5 页：系统功能总览
====================

游客端首先支持自然语言问答。用户可以问“停车还有空位吗”“我的积分多久过期”“沃德面包在哪里”“今天有什么优惠”。系统会根据问题类型选择不同工具，而不是让大模型凭记忆回答。

第二项能力是智能规划。系统支持约会、家宴、挑礼物、带娃和商务接待等场景。大模型会记住时间、人数、预算、口味等槽位，查询真实店铺、排队和营业状态，生成结构化方案，并提供“用时最短”和“路程最近、回头路最少”两种策略。

第三项能力是方案持续修改。用户可以说“再加一家店”“删除某店”“把某店放最后”“换到晚上”“少走路”，也可以表达更自然的增量要求，例如“在原方案里增加一个晚上七点吃饭的活动”。系统不是针对每句话写一个专项 if，而是让大模型输出通用的 add、remove、replace、move、reorder、set_time、update_slots 和 set_strategy 操作，再由后端应用到当前方案。

第四项能力是地图导航。系统将方案中的店铺映射到走廊入口节点，路线只能经过走廊；不能穿过店铺、卫生间、服务台、瀑布厅、电梯实体区域等占用空间。跨楼层默认经过直梯，用户也可以选择扶梯。小程序使用轻量 2.5D 地图，Web 使用 three.js 交互地图，并播放同一份路线数据。

第五项能力是预约与优惠。用户可以在预约页按楼层筛选和搜索餐厅，自定义时间和人数，查看“我的预约”，并取消或修改预约时间及人数；也可以直接通过 LLM 发出预约、取消和修改指令。商户发布的套餐或代金券会同步到顾客端，领取失败时返回真实业务原因，而不是显示 unavailable 这种内部状态词。

第六项能力是语音播报。规划摘要可以通过后端 TTS 生成普通话音频，小程序点击“播报”开始播放，再次点击停止。


第 6 页：效果视频与现场演示
==========================

这一页建议不要只放一段没有说明的视频。建议在视频旁边写出演示链路，让老师知道视频验证了什么。

演示从三方入口开始。我们先以游客身份登录并扫描 AI 服务码，二维码中的 scene 会被后端解析为服务码，再映射为 mall_id 和当前入口节点。

进入星河里后，先询问停车和积分规则，分别展示结构化数据库查询和 RAG 知识检索。然后输入一个自然语言规划目标，例如“今晚七点两个人约会，想吃川菜，之后喝点东西，尽量少走路”。系统生成方案后，我们继续用自然语言增加、删除或调整站点，验证文字、方案卡片和地图同步变化。

随后确认方案。只有确认后，系统才执行预约或领券等写操作。最后切换到预约页查看刚才创建的预约，再进入地图播放走廊路线。

如时间允许，还可以进入商户端修改排队时间或发布代金券，再返回游客端查询，展示双方读取的是同一份后端数据。


第 7 页：四层总体架构
====================

系统总体分为四层。

第一层是客户端层，包括微信原生小程序和 Vue 3 Web。小程序兼顾真机和低配设备，Web 适合大屏展示、管理驾驶舱和三维地图。两端只在登录方式和交互呈现上有区别，业务状态来自同一后端。

第二层是统一接入层，由 FastAPI 提供认证、会话、权限和统一响应。游客手机号登录、微信 code2session、商户店铺编码登录和管理者登录最终都会形成后端签名 Token。所有普通接口统一返回 code、message、data、request_id 和 timestamp。二维码 scene 在这一层解析为 mall_id 与入口节点。

第三层是 AI 智能体与业务编排层。在线使用 qwen-plus，接口遵循 OpenAI-compatible 协议；失败时自动进入 scripted fallback。Conversation Intelligence 负责意图、槽位和多轮上下文；Planner Agent 使用八状态流程；Function Calling 工具注册表负责查询私有数据；结构化方案校验器保证模型输出合法；Direct Business API 让停车、会员、优惠和预约等页面即使不经过 LLM 也能工作；导航、事务和语音服务分别承担确定性执行。

第四层是私有数据与资源层。SQLite 保存商场、用户、店铺、实时状态、停车、会员、优惠、预约、方案和经营指标；RAG 目录保存规则和服务指南；地图目录保存楼层图、店铺入口、设施、障碍物和走廊图；Datasource Registry 根据 mall_id 选择对应数据适配器。

底部的安全、可靠性和可观测能力贯穿四层，包括角色授权、mall_id 隔离、确认门、方案版本与幂等、注入测试、请求日志、健康检查、数据库备份、自动测试、冒烟测试和 LLM 降级。


建议新增第 8 页：LLM 为什么不是摆设
=================================

我们对 LLM 和确定性后端进行了明确分工。

LLM 负责理解自然语言、识别用户是在查询还是规划、承接多轮上下文、补全槽位、选择工具、生成方案操作和解释推荐理由。后端负责身份、mall_id、数据库事实、路线计算、冲突校验、权限和事务落库。

这套分工解决了两个常见问题。

第一个问题是幻觉。大模型不能直接编造店铺、余位或优惠，也不能自己传入 mall_id 和 user_id。工具执行前会删除模型提供的权限字段，再从认证会话中注入真实上下文。

第二个问题是“文字和实际方案不一致”。模型的文本不会直接作为最终方案。后端先生成或修改 canonical plan，验证店铺 ID、楼层、营业状态、时间冲突和活动数量，再重新计算路线；最终回复、方案卡片、地图和确认事务都引用同一组 store_id。

例如用户说“在现有方案基础上增加一顿晚上七点的晚餐”，模型会生成增量 patch，而不是重新生成两个同时七点开始的餐厅。即使在线模型偶尔返回了不合理的完整方案，差异校验层也会尝试转换成增量操作，避免覆盖已有行程。

Planner 的完整状态是：IDLE、UNDERSTAND、COLLECT、PLAN、ROUTE、CONFIRM、EXECUTE、DONE。刷新或换端后，可以根据同一 user_id 和 session_id 恢复状态；在 CONFIRM 前不会写入预约、优惠券或票券。


建议新增第 9 页：私有数据、知识库与“一码一所”
=============================================

我们没有把所有信息都塞进知识库，而是根据数据性质分开处理。

积分有效期、生日月规则、积分兑换和商场服务指南属于稳定的非结构化规则，存放在 server/data/knowledge 下的 Markdown 文档中。轻量 RAG 会按 mall_id 过滤文档，对中文双字词和关键词评分，返回文档名、章节、片段和分数；没有证据时明确回答“知识库未提供这一规则”。

餐厅营业、排队、余位、优惠库存、我的预约和停车空位属于实时结构化事实，必须查询 SQLite，不能使用可能过期的知识文档。规划则同时使用 LLM、结构化工具、当前方案和地图路网。

“一码一所”的实现不是让二维码直接携带数据库地址。二维码 scene 只携带服务码，后端的 mall_service_codes 将服务码解析为 mall_id 和 entry_node，再绑定到会话。之后 Registry 和每条业务 SQL 都使用会话中的 mall_id 过滤。即使用户或模型尝试在参数中覆盖 mall_id，后端仍以扫码会话为准。

当前演示配置了 mall_demo 与 mall_alt 两个逻辑租户，用于自动验证不同商场之间不会串店铺、会员和事务数据。课程阶段采用同一个 SQLite 数据库按 mall_id 行级隔离，未来可以保持接口不变，将 Registry 的适配器替换为独立数据库或真实商场 API。


建议新增第 10 页：地图路线为什么可信
===================================

地图分成“呈现资源”和“可计算路网”两部分。

呈现资源包括楼层、店铺方块、卫生间、服务台、电梯、扶梯、瀑布厅、消防安保和其他非商户设施。设施会显示在 Web 与小程序中，但不能作为可预约商户热点。

可计算路网包括走廊节点、店铺入口节点、换层节点和边。店铺目的地位于临走廊入口，而不是店铺中心。Dijkstra 在图上计算最短路径，障碍物和占用区域不会成为可通行节点，因此路线不会穿墙或穿过店铺。

跨层时，默认垂直模式为 elevator；如果用户明确要求扶梯，才切换到 escalator。路线接口返回 floor、node_id、x、y、type、label、polyline_segments 和 transfer_instruction，因此前端只负责渲染和播放，不自行猜路线。

需要明确说明：当前星河里底图是课程 Demo 仿真地图，没有接入真实室内定位，所以我们不声称实现了生产级数字孪生或实时定位；但路网建模、路径算法、楼层换乘和动画数据链路都是真实实现。


建议新增第 11 页：事务、权限与运维保护
=====================================

所有会改变数据库的操作都经过确认门。预约、取消预约、修改时间和人数、领券以及套餐购买，必须携带当前用户会话和确认信息。Planner 只有从 CONFIRM 进入 EXECUTE 后才能执行写工具。

方案和提示词都带 revision。前端修改时提交 expected_revision，如果另一个页面已经保存了新版本，后端会返回冲突，避免旧页面覆盖新数据。重复确认同一个方案会返回原结果，实现幂等，而不是重复创建预约。

系统启动脚本不会随意重置演示数据库。日常启动会先备份并检查数据库完整性；自动测试、冒烟和压测使用独立临时数据库，避免破坏现场已有 Plan、预约和优惠券记录。在线大模型异常会记录 degraded 原因并切换 scripted fallback，TTS 不可用时也会明确标记降级，不伪装成功。

安全方面，后端同时校验 Token channel、mall_id、user_id、merchant_store_access 和 manager_access。测试覆盖无 Token、跨用户、跨商场、跨角色、确认绕过、SQL 注入和 Prompt 注入。密钥、微信 session_key、完整 Token 和密码不写入日志。


第 12 页：技术栈与为什么这样选择
================================

小程序使用原生 WXML、WXSS 和 JavaScript，减少运行依赖，适合微信生态和低配设备。Web 使用 Vue 3、Vite 和 Vue Router，便于大屏展示和组件化开发。三维地图使用 three.js 与 OrbitControls，实现轻量楼层旋转、缩放、店铺互动和路线动画。

后端采用 Python、FastAPI、Pydantic 和 uvicorn。FastAPI 提供清晰的请求模型、自动 OpenAPI 和适合工具编排的接口结构。数据库使用 SQLite，是因为课程 Demo 数据量有限，需要稳定、便携并支持真实事务；我们明确没有把它包装成多库集群。

大模型采用 OpenAI-compatible 接口接入 qwen-plus，避免业务代码与单一模型厂商深度绑定。Scripted Agent 不是替代大模型，而是断网演示兜底。RAG 使用本地 Markdown 与轻量关键词检索，适合小规模、可解释的规则文档，没有为了架构名词引入不必要的向量数据库、LangChain、Redis、消息队列或微服务。


建议新增第 13 页：测试与验收证据
=================================

项目不是只完成页面后进行人工点击，而是建立了自动化验证。

截至验收报告，pytest 共 20 项全部通过，覆盖登录、二维码解析、RAG 来源、mall_id 隔离、中文槽位、五类规划、双策略、直梯与扶梯切换、走廊约束、店铺编码一致性、确认门、目的地动画、商户同步、管理驾驶舱、跨角色阻断和注入防护。

全链路 smoke_demo 连续运行两次均通过，每次 17 个请求、0 错误，五种规划场景都到达 DONE。

专用轻量压力测试在 scripted 模式下使用 16 并发执行 120 个 health、parking 和 chat 混合只读请求，120 次全部成功、0 错误；最新专用报告记录平均 95.76 毫秒、P50 92.46 毫秒、P95 163.86 毫秒、吞吐约 152.54 请求每秒。这里使用 scripted 是为了避免压力测试消耗线上模型额度，测量的是后端接入、数据和本地编排能力。

Web 构建成功，小程序 JavaScript 和 JSON 均完成语法检查；浏览器验收覆盖三方入口、管理驾驶舱、商户运营台、游客导航浮层以及普通问答不误触发地图。在线千问也完成过真实工具调用验证，并保留自动降级。


第 14 页：总结、边界与展望
==========================

我们的核心成果可以概括为四点。

第一，我们完成了微信小程序和 Web 双端共用的统一后端，而不是两套孤立页面。

第二，我们让 LLM 真正参与意图理解、多轮槽位、工具选择和方案修改，同时用结构化校验、canonical plan 和确认门约束模型，使大模型能够参与业务但不能越过权限和事实边界。

第三，我们把私有结构化数据、RAG 规则文档、室内路网和事务服务组合起来，实现从问答、规划、路线、确认到预约和领券的闭环。

第四，我们补充了角色隔离、方案版本、幂等、数据库备份、健康检查、降级、自动测试和压力测试，使系统在演示环境中具有可维护性，而不是一次性的展示代码。

当前限制也需要诚实说明：地图是仿真底图，没有真实室内定位；管理指标是演示快照；预约、票券和停车来自课程私有数据源，没有连接真实商业平台；正式上线还需要微信正式发布与 HTTPS 合法域名、真实商场地图标定、停车和会员系统 API、生产密钥管理、限流、审计、高可用数据库和合规评估。

未来扩展时，我们会保持前端契约和工具 Schema 不变，通过 Datasource Registry 接入真实商场数据，并将当前仿真地图替换成经过人工校准的正式地图资产。

答辩时主动补充的高频追问口径
============================

一、为什么不把餐厅和预约也放进知识库？

因为营业、排队、余位和预约是实时结构化事实，必须直接查数据库；RAG 只处理积分规则、服务指南等稳定文档。这样可以避免文档过期与数据库事实冲突。

二、大模型是否能直接改数据库？

不能。模型只能选择工具和给出结构化参数；后端注入真实身份和 mall_id，写工具还必须通过确认门。

三、为什么需要 scripted fallback？

在线大模型负责开放式理解，scripted 只在网络或模型不可用时维持可演示的固定能力，并且响应会明确标记 degraded，不冒充在线模型。

四、二维码如何对应不同商场？

二维码携带 service_code，后端映射为 mall_id 和入口节点，再将它绑定到 session。新增商场需要新增服务码、数据适配器和地图资源，不需要改客户端主流程。

五、是不是所有人都能扫开发版二维码？

开发版和体验版受到微信成员与体验权限限制。要让普通用户长期扫码使用，需要提交审核并发布正式版，同时配置 HTTPS 合法域名。

六、地图是不是实际商场导航？

路径算法和走廊路网是真实计算，底图和坐标属于课程 Demo 仿真；没有接入真实室内定位，因此不宣称生产级导航。

七、为什么没有使用 LangChain 或向量数据库？

项目知识量有限，直接工具注册表、状态机和轻量关键词 RAG 更容易解释、测试和控制。引入大型框架不会自动提高准确率，反而会增加演示风险。

八、两端状态如何同步？

两端使用同一 user_id、session_id、Token 语义和 SQLite 数据。方案、预约、优惠券和商户状态由后端保存，不保存在某一端的临时页面中。

九、提示词能否人工维护？

可以。核心提示词独立位于 server/app/prompts，管理者双端界面都能读取、编辑、保存、查看 revision，并恢复上一版本；旧 revision 并发保存会返回冲突。

十、项目最值得强调的创新是什么？

不是单独使用了某个大模型，而是把自然语言理解、私有结构化数据、RAG、可计算室内路线、事务确认和双端状态统一为一个可验证闭环，同时用 canonical plan 解决了模型文字和实际执行不一致的问题。
